====================================================================
  ROSE ASSET HUNTER
====================================================================

Find out what any texture or model in ROSE Online is called.

  Double-click "ROSE Asset Hunter.pyw".  Nothing to install.

  The .pyw ending is deliberate -- it stops Windows opening a
  black console window behind the app.


--------------------------------------------------------------------
WHAT IT IS FOR
--------------------------------------------------------------------
ROSE assets do not tell you what they are. A texture is just pixels, a
model is just triangles, and a particle file does not even contain its
own filename.

So the first problem in any mod is finding out WHICH file you need,
and nothing in the game will tell you. People end up guessing, or
replacing files one at a time to see what changes.

This makes the game tell you instead.


--------------------------------------------------------------------
TWO WAYS ROUND
--------------------------------------------------------------------
FORWARD -- "what IS that thing?"
    Pick a folder, install markers, go and look. Whatever you are
    chasing will have its own name written across it.

BACKWARD -- "where is this USED?"
    Type a filename into the box and press Find it. Every place that
    file is drawn will light up at once.

    This doubles as a search -- but read an empty result carefully. It
    means the tool cannot find that name, not that the file is absent.

    Names and pixels are stored apart in the archive, and some assets
    are real and in use with no readable name entry. _critical_01.dds
    is one: it exists, and a search for it comes back with nothing.

    IF YOU HAVE A NAME TABLE, this can use it. Put a file called
    rose_names.json next to the app -- a list of entries saying
    {"name": ..., "offset": ..., "length": ...} -- and effects,
    textures, meshes and sounds will show their real filenames instead
    of an offset.

    NONE IS INCLUDED, and nothing is downloaded. Without one, the tool
    behaves exactly as it always has.

    Every entry is CHECKED against your own archive before it is used:
    is there really a texture at that offset, does it really run that
    long. Anything that points somewhere else is dropped and the count
    is reported. A name that is wrong is worse than no name at all --
    you would edit the file it told you to and not find out for weeks.

    Effects are read a different way and are not affected by this --
    every particle record in the archive is found, aligned or not.

    So an empty result means "not found", never "not there". Marking a
    texture and looking at it in game is the reliable method; searching
    by name is the convenient one.


--------------------------------------------------------------------
HOW TO USE IT
--------------------------------------------------------------------
1. Point it at your ROSE Online folder.
2. Press "Read the archive". This lists every texture and model the
   game names, so you pick from what is REALLY there rather than from
   a guess.
3. Pick a folder. The files inside appear below it -- take the whole
   folder, or select individual files, or filter to only textures or
   only models. Or type one filename in the box to find it wherever
   it lives.
4. CLOSE THE GAME, press "Install markers", then start it and look.
5. Press "Restore everything" when you are done.

Anything that takes a while -- reading the archive, extracting,
browsing -- can be stopped with the Cancel button. It stops at the
next safe point rather than being killed, so nothing is left
half-written.


--------------------------------------------------------------------
THREE WAYS OF MARKING
--------------------------------------------------------------------
NAMES ACROSS IT
    The default. Good for anything reasonably large.

NAMES SIDEWAYS
    For tall thin things. Some effects draw particles as narrow
    vertical slivers, and flat lettering gets squeezed into something
    unreadable. Turning it a quarter turn puts the name along the long
    axis instead.

FLAT COLOURS
    For very small things. Colour needs no resolution -- one lit pixel
    still carries its hue -- so when a sprite is a few pixels across,
    colour is all that survives.

    A colour says nothing on its own, so a key naming every colour is
    written to ROSE_HUNT_KEY.txt in your game folder. Restore removes
    it along with everything else.


--------------------------------------------------------------------
WHERE MARKERS DO NOT HELP
--------------------------------------------------------------------
INTERFACE ART. Window frames and gauges are cut from an atlas one or
two pixels at a time, so a name written across the file never appears
whole on screen -- you get a sliver of a letter. Marking still tells
you WHICH atlas changed, which is usually the question, but it will
not read as text.

PARTICLE FILES AND EFFECT WRAPPERS cannot be marked at all. Those
records do not contain their own names, so there is nothing to label.
Find the textures an effect uses instead and work backwards.

Some things are encrypted and out of reach entirely -- fonts, some
model chains, and part of the archive index.


--------------------------------------------------------------------
LOOKING BEFORE YOU PULL
--------------------------------------------------------------------
"Browse textures..." shows the textures inside the app, read straight
out of the archive. Nothing touches your disk until you pick one.

Click a thumbnail to select it, ctrl-click to add more, then press
"Save selected" -- only those files are written, each as a .dds you can
edit and a .png you can look at.

Sort by where it was found, by size, by format, or BY COLOUR. Colour is
the one worth knowing about: effect textures are mostly one hue each,
so all the fire lands together and all the ice lands together, and you
can often spot what you want without knowing anything about it.

That is usually the better way round: find the thing you want, take
only that, instead of extracting thousands and searching through them.

You are asked for a size band first, because that is what makes the
grid a page instead of a wall. Reading stops when you press Stop
reading, or at 600 textures.


--------------------------------------------------------------------
GETTING EVERYTHING OUT AT ONCE
--------------------------------------------------------------------
"Extract textures..." pulls every texture in the archive out to a
folder, each saved as a .dds and a .png you can look at.

Marking tells you WHAT something is. This gets you the pixels, which is
what you need if you want to RECOLOUR something rather than redraw it
-- and redrawing from scratch is how a lot of mods end up looking like
a different effect wearing the same name.

They come out NUMBERED, not named. The archive index cannot fetch a
file by name -- its offsets are not positions you can seek to, and
land in unrelated data -- so textures are found by their own header
instead. That recovers the pixels but not the filename, because the
two are stored apart.

Everything lands in a folder of its own, named with the date, and
sorted inside that by format and then by dimensions:

    ROSE_Extract_2026-09-06_0111/
        raw/256x256/
        DXT1/512x512/

So it never scatters loose files into whatever folder you picked.

You are asked which SIZES to pull before it starts. That matters --
everything is a few thousand files that are miserable to search, while
one size band is usually a few dozen. You cannot ask for a file by
name, but you can ask for its shape.

In practice: pick the band, sort by size in Explorer, turn on large
thumbnails, and the one you want is usually obvious.


--------------------------------------------------------------------
GETTING THE INTERFACE FILES OUT
--------------------------------------------------------------------
"Extract interface files..." saves every interface document and
stylesheet as readable text.

This is the one worth reaching for most often. Every interface change
starts by reading one of these -- what a window is made of, which
sprite rectangles a sheet declares, which colours a theme sets.

Unlike textures, these come out PROPERLY NAMED, because they say what
they are: a document declares <body id="hud">, and a stylesheet names
the image it draws from. So you get hud.html and stateicon.css rather
than numbers.

    documents/     the windows -- hud, minimap, chat, inventory ...
    stylesheets/   the sprite sheets and theme colours

Both are plain text. Edit a copy, drop it in the matching folder under
your ROSE install, and the game will load yours instead -- documents
and most stylesheets are read from disk in preference to the archive.


--------------------------------------------------------------------
LOOKING AT MODELS INSTEAD OF REPLACING THEM
--------------------------------------------------------------------
"Browse models..." reads the game's models straight out of the archive
and draws each as a wireframe. Nothing is installed, so nothing can
crash.

This is the better answer to the model problem. Marking models to find
out what they are will often take the client down, and the crash report
cannot say which file did it -- but nothing stops us simply reading
them and drawing what is there. A wireframe is enough to tell a sword
from a shield from a ring.

Selected models can be saved as a plain text list of points and
triangles.


--------------------------------------------------------------------
A WARNING ABOUT MODELS
--------------------------------------------------------------------
Replacing textures is safe. Replacing MODELS can crash the game --
some are animated by data that expects an exact shape and will not
accept a substitute.

Models are switched OFF until you tick the box, and the game will warn
you again before writing. Nothing is damaged if it crashes: press
Restore and it is fine.

MOST MODELS ARE ACTUALLY FINE. All 133 meshes in effect\effectmesh
were marked one at a time, and 124 of them worked. Nine did not:

    _jemitem_01 .. _jemitem_06
    _pumpkin_01
    _warp_join_01, _warp_join_02

Those nine are refused now. Why those nine is still unknown -- they
fall into three families, which points at something structural rather
than nine separate faults, but nothing here can see the difference yet.

So the warning stands, and it is narrower than it was: models are
worth trying, and the ones known to fail are named.

TERRAIN TILES CANNOT BE MARKED AT ALL, and the app refuses rather than
letting you try. The game loads a tile set as ONE thing and rejects it
unless every tile agrees on size and format. Its own words:

    All terrain textures must be the same dimensions, image
    'S002_01.dds' with size 128 x 128 does not match previous image
    'T025_01.dds' with size of 256 x 256.

    All terrain textures must be the same compression format, image
    'S002_01.dds' with format RGBA8 does not match previous image
    'T025_01.dds' with format of BC3.

Markers are 128x128 and uncompressed; those tiles are 256x256 BC3.

Marking the WHOLE folder does not rescue it. Every one of the 109
names the archive gives for junon\jg was marked and the game still
objected about T025_01.dds -- a tile it loads that is not in the name
list at all. The set cannot be made to agree because the set cannot
be seen.

Use Browse textures for terrain instead. Nothing is installed, so
there is nothing for the game to refuse.

Some map and character TEXTURES can still crash it, for the same
reason -- the client expects a particular size. Those get a warning of
their own.

BE CLEAR ABOUT WHAT THE WARNINGS ARE. They do not prevent a crash and
cannot -- there is no way to know in advance which assets the client
will refuse. They tell you a crash is LIKELY so it is not a surprise.

AND THE CRASH REPORT CANNOT TELL YOU WHICH FILE DID IT. A Windows
minidump records the call stack as addresses inside trose.exe. Turning
those into names needs the symbol file Rednim builds and does not ship,
and even with it the answer would be "crashed inside the mesh loader",
not "crashed on this file" -- the filename is a local variable a dump
does not keep.

SO BE HONEST ABOUT MARKING MODELS IN BULK: it is not much use. Marking
a whole folder of models will often just crash, and nothing tells you
which one caused it.

Where model marking DOES earn its place is when you already know the
name and want to see where it is used -- one file, one question, no
guessing. Use the file list to pick individual models rather than
taking a folder at a time.



MARKING EFFECTS
    The same idea as marking a texture, one level along. Pick some
    effects, and each is replaced by a marker drawing its own NUMBER.
    Go and do the thing you are chasing, and whichever number appears
    is the effect that fired. The numbers are listed in
    ROSE_HUNT_KEY.txt next to the game.

    This is how c_hit_01 was found -- the effect that draws every
    ranged critical in the game and has nothing in its name to say so.
    Searching by name had failed for two days. Sixteen numbered
    markers answered it in one fight.

    A NAME TABLE DOES NOT REPLACE THIS. A table tells you what an
    effect is CALLED. It cannot tell you which one FIRES when you do
    something, and in this game those come apart badly:

      ATSPEED_UP_01.PTL   named for the attack speed buff, never plays
      DEFENDUP_01.PTL     actually draws the attack speed buff
      c_hit_01.PTL        draws every ranged critical

    Keep the selection small. Sixteen or so is comfortable; a hundred
    numbers on screen tells you nothing.

    Effects are marked on their own -- not mixed with textures in the
    same run -- because they are written differently.

SOUNDS
    Browse sounds lists every piece of audio in the archive with its
    length, channels and bitrate. Long ones are usually music, short
    ones are effects.

    There are TWO kinds in there and the list says which:

      WAV   sound effects. These play in the app, straight away --
            nothing to install, no codec.
      OGG   music. Windows will not play Ogg inside the app (tried),
            so these open in whatever player you already have. If it
            asks for a codec, that is Windows, not this.

    Nothing is decoded to build the list. Both formats state their own
    channels, sample rate and length in plain fields before any
    compressed audio begins -- so the whole archive is described
    without touching a single sample.

    Save selected writes them out as ordinary .ogg files.


--------------------------------------------------------------------
WILL IT WORK ON MY VERSION?  WILL AN UPDATE BREAK IT?
--------------------------------------------------------------------
Probably yes, and probably not -- because of how it finds things.

It does not know any file paths, offsets or version numbers. It finds
assets by what they ARE: a texture begins with the letters DDS, a model
begins with ZMS, an effect file has a structure that only a real one
satisfies. Those have not changed in twenty years and are the same in
every build and on every server.

So:

  A GAME UPDATE            should change nothing. Names and positions
                           move; the tool re-reads them every time and
                           never remembers where anything was.

  A PRIVATE SERVER         should work, and sometimes better. Many run
                           older clients with less locked down, and the
                           folder list is built from whatever that
                           install actually contains rather than from
                           assumptions about it.

  A VERY OLD CLIENT        the textures and effects should be fine.
                           Models are read as ZMS version 7 and 8; an
                           older version would simply not appear.

THE ONE THING THAT WOULD BREAK IT is the archive being encrypted. The
index file, data.idx, ALREADY IS on the current official client -- it
used to hold a readable list of filenames and no longer does. If the
main archive ever goes the same way, nothing here can read it and no
amount of fixing would help.

That is worth knowing before relying on it. Everything this does
depends on the archive being readable, and that is somebody else's
decision.


--------------------------------------------------------------------
IS THIS SAFE FOR MY GAME?
--------------------------------------------------------------------
Yes, and here is exactly why.

ROSE loads loose files in preference to the ones in its archives. This
tool only ever writes loose files -- it never opens, edits or damages
rose.vfs or anything the game shipped with. Deleting what it wrote
puts everything back precisely as it was.

It records every file it writes, so Restore removes exactly those and
touches nothing else.

It does not talk to the server, does not change how the game plays,
and gives no advantage. It is a way of reading labels.


--------------------------------------------------------------------
WHY IT RE-READS THE ARCHIVE EVERY TIME
--------------------------------------------------------------------
It would be faster to save the list. It once was, and that list
quietly covered only about 62% of what the archive actually names -- so
a long search failed for days, looking through a set that never held
the answer.

The scan takes a couple of minutes. It is worth it.
